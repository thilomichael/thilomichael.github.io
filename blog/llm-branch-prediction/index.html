What is a branch predictor?

In a nutshell, the CPU (the small rectangular hot part in your vibe coding machine) is like a pipeline: each instruction has to be prepared ahead of time so it can load data, shuffle around some registers and make it all cozy, and when the time comes and the instruction has to be executed, everything is warm and ready. And because all that warming up takes a while, the CPU doesn’t wait for one instruction to finish before it starts on the next one: there’s always a whole queue of instructions in the pipeline at the same time, each one a little cozier than the one behind it.

Put yourself in the shoes of the CPU for a moment: whenever there is a conditional jump, a.k.a. a branch (every if, for and while has one), your pipeline runs dry, because you would need to know which way the condition resolves in order to continue filling it up. But now you are very special and have the brilliant idea to just guess whether the branch gets taken. So you start loading up the pipeline for that prediction. If the guess is right, your psychic abilities have already paid off. If it’s wrong, your precious work is discarded and you load the right instructions instead. That’s just what you would have had to do anyway, so a wrong guess costs you (almost33 If you ignore that one tiny little oopsie called Spectre.) nothing!

Given that neither the Daily Karmic Number nor the most recent horoscope is available to the average CPU, there are actual strategies to guesstimate whether a branch gets taken. In practice, the branch predictor gets to see the location of the branch and it knows the outcomes of previous branches. With that, the classic textbook predictor, the 2-bit counter, keeps a counter for every branch and just counts it up whenever that branch is taken and down whenever it isn’t (capped between 0 and 3). If the counter is currently at 0 or 1, it predicts “not taken” – if it is at 2 or 3, it predicts “taken”. The strategy is basically “I’m just doing what was correct last time”, but with a small buffer, so the winning streak is not interrupted by an occasional single untaken branch.

In reality, modern CPUs use far more advanced branch predictors that try to squeeze out every possible bit of information from these very limited inputs. In fact, there are even branch predictors that use small neural networks in order to find every hidden branch pattern inside your badly written while loops. AMD advertised its first Ryzen CPUs in 2017 with a “Neural Net Prediction”. So, the idea to use AI to predict branches has basically already been tested in production. Speaking of neural networks, how about we use an unartificial unintelligence (yes, I mean you) to do it? You get to see exactly what a branch predictor sees: which loop it is and what it did before44 Well, I’m giving you a little head start: an actual branch predictor doesn’t know how long the list is.. Will you have what it takes to be a real branch predictor?

Jev, you’re hired

Alright, I like your effort, but we really need something faster, and compared to a human or any LLM, Jev is much faster.

In order to benchmark how well my advanced AI branch predictor is doing, I wrote two reference algorithms: a bubble sort that sorts 12 numbers, and a binary search that looks up 20 random numbers in a sorted list of 64. This sums up to 417 branches in total that I recorded by replacing every conditional with my own branch recording function:

def bubble_sort(a: list[int]) -> list[int]:
    n = len(a)
    i = 0
    while br(site="bubble:outer", cond=i < n):
        j = 0
        while br(site="bubble:inner", cond=j < n - 1 - i):
            if br(site="bubble:swap", cond=a[j] > a[j + 1]):
                a[j], a[j + 1] = a[j + 1], a[j]
            j += 1
        i += 1
    return a

def br(site: str, cond: bool) -> bool:
    # The real br-function also saves local variables, more on that later
    TRACE.append({"i": len(TRACE), "site": site, "taken": cond})
    return cond

So after the runs, I can inspect every decision and which path was taken. Now Jev comes into play: I put it into noul-mode (whatever that means) and prompted it with “A CPU is about to run this branch. Will the branch be taken this time?”. For every recorded step of the algorithm, I built up some context containing the last 16 results of that branch and the last 16 results of all branches together55 That’s what real branch predictors look at too: the history of the branch itself (its local history) and the history of all branches (the global history), because branches often depend on each other. and let Jev handle the prediction.

The result was very disappointing – maybe I overestimated my and Jev’s system one intelligence: the results are within spitting distance of just using the 2-bit counter. In fact, it guessed exactly what the 2-bit counter guessed on 393 of 417 branches and didn’t see a single exit coming either. At least we are burning almost 17 thousand US dollars on one single second of CPU time66 The cost per second assumes a billion branches per second for one CPU core.. That’s quite a feat given how cheap these predictions are.

I thought maybe, just maybe, the prediction is so bad because Jev only sees the 16 previous results and not the whole history. Turns out, giving it too much context makes it worse: prediction accuracy dropped to 62.1%, but at least the price per second increased to $48,800.

To be honest, I was very disappointed with Jev, but couldn’t let the thought of a really accurate branch predictor go, so I switched gears and went for something more system-two-ish.

But I was not at the end of my rope yet.

Let it read the code

Okay, what else can we try? Sure, let the LLM read the code that is being executed, so it can understand and reason about what must happen when. Well, I added the program itself, how its input is made, and every earlier branch – basically everything except the contents of the variables themselves, because that would be cheating, right? Right?

Sadly, even that doesn’t really make a difference: Haiku gets slightly worse at 69.3% and Jev gets a little bit better at 73.6%. With blind determination, I went to the bank and got a loan that I directly invested into more Claude API credits. I activated thinking and watched the tokens fly across the screen.

Wait. With thinking, at almost $550,000 a second, Haiku was still no better than Jev (and only marginally better than a 2-bit counter)? That doesn’t make sense, right (foreshadowing intensifies)? So I investigated a bit, played around as a branch predictor myself and pretty soon came to the conclusion that there is a theoretical limit. With only the history, about 78% is the most anyone can get (I did the math with my brand new Jev calculator), because every loop exit comes as a surprise. With the code, you can at least count the loops, which raises the limit to about 84%. But even with all the time and money in the world, without the contents of the variables nobody can know whether two numbers are about to be swapped, or whether the number we’re looking for is in the left or the right half of the list. Everything above that is only possible if you have the data.

So the verdict is: even with thinking and code, Haiku still can’t reason its way to the theoretical limit and falls around 10 percentage points short. Sure, we are still not out of options, but I really have to start raising some real venture capital in order to keep the business going.

Of course, without the actual contents of the list it still can’t predict every swap, but it can use the results of the earlier swaps and a bit of pure logic to deduce the outcomes. The result?

Just give it the answer

I don’t know if you noticed, but 77.3% is not quite 100%. The hunt for the best branch predictor is not over. How can a branch predictor know exactly which outcome to predict? Well, a perfectly intelligent system that knows the code, the contents of the variables and all of the history of the world could easily say what the outcome of an if statement is. So let’s build that!

You might say, “Just use a CPU to run the parts before the branch, then you can predict it no problem!” But your argument has a fatal flaw: that CPU would also need a branch predictor to be fast and efficient. In contrast: an LLM is pure matrix multiplication and can be implemented completely branchless77 Except for the loop that generates one token after the other until it’s done. But that’s just one branch, how hard can it be?. Also, it runs in the cloud, so you don’t have to worry about all the computing that’s going on there. Just go with the vibes!

I say BLASPHEMY! Of course I thought of that and just downloaded Qwen 3.5 35B, hooked it up to my branch prediction code and there you go: AI branch prediction – even on an airplane!
